# Płynność aplikacji i podglądu — paczka 16

Baza: `fbfa0514517d0acdba714d5f8e0c88e38fc97e57` (zainstalowana paczka 15).
Wersja widoczna w Profilu oraz Pomocy i FAQ: `2026.10.29.16`.

## Zmiany

- Dzienne dopasowanie sesji i prezentacja tygodnia korzystają z osobnego
  `sessionRuntime.ts`. Otwieranie zapisanej aplikacji nie pobiera całego generatora
  planów. Publiczne eksporty `planEngine.ts` pozostają dostępne dla dotychczasowych
  wywołań; generowanie nadal odbywa się przez istniejący worker lub import dynamiczny.
- Start zapamiętuje wynik obliczenia planu do czasu zmiany jego danych. Otwarcie
  okienka nie przelicza całego planu ponownie. Plan analogicznie zapamiętuje tygodnie.
- Zmniejszanie obciążenia sesji wykonuje wspólne obliczenie dawki jeden raz.
- Start i Plan mogą przygotować kod sąsiedniej zakładki po 700 ms, w wolnej chwili
  przeglądarki. Zadanie jest anulowane przy zmianie ekranu i pomijane offline,
  przy oszczędzaniu danych, wykrytym 2G/3G, małej przepustowości lub ukrytej karcie.
  Nie uruchamia z wyprzedzeniem kamery, Lab, Fuel ani IQ.
- Podgląd Vite przygotowuje na serwerze najczęstsze ekrany. Dwie biblioteki
  serializacji są przetwarzane razem z zależnościami zamiast wysyłania ich surowych
  wersji. Zachowano konfigurację i transformacje routera wymagane przez Lovable.
- IQ nie tworzy i nie próbkuje drugiej symulacji, kiedy otrzymuje już gotową
  klatkę. Odczyt szerokości boiska następuje przed zmianami etykiet w danej klatce.
- Kompilacja web i mobilna zatrzymują się, jeśli pełny generator ponownie trafi
  do statycznych importów kodu startowego. Osobny import dynamiczny jest dozwolony.

W tej paczce nie ma zmian schematu bazy ani nowych zależności npm. Zasady treningowe,
wersja silnika i format zapisanych planów pozostają zgodne z paczką 15. Nie trzeba
kasować danych ani generować planu ponownie.

## Weryfikacja

Node 22.23.4, npm 11.9.0. Kontrola `npm run verify:release` obejmuje TypeScript,
1471 testów w 166 plikach, ESLint oraz kompilacje web i mobilnego SPA. Wszystkie
te etapy przeszły. Nowe testy sprawdzają ograniczenia przygotowania zakładek,
anulowanie zadania, używanie gotowych klatek IQ oraz statyczne importy generatora.
Porównano także kompletny syntetyczny plan 28-dniowy przed i po rozdzieleniu kodu:
wynik jest identyczny poza losowym identyfikatorem cyklu.

Chromium 390 × 844: Start, Plan, Fuel, Progres i IQ na syntetycznym koncie z
zapisanym planem, a także 9 publicznych scenariuszy wejścia (w tym blokada
localStorage) — bez błędów JavaScript. Wersja 16 jest widoczna w FAQ.
Osobno uruchomiono webowy SSR przez Wrangler: `/demo` i `/faq` zwracają 200,
nieistniejąca trasa zwraca 404 z właściwym ekranem. Konfiguracja podglądu Lovable
zachowuje wymagany host i port oraz nowe przygotowanie ekranów.

### Pomiary lokalne przed i po

Te liczby dotyczą kontrolowanego testu, a nie pomiaru na telefonie użytkownika.
Chromium: procesor spowolniony 4 razy, opóźnienie sieci 80 ms, pobieranie 6 Mb/s.
Każde wejście używa nowego kontekstu przeglądarki. Syntetyczne konto ma lokalny
zapis planu i zaakceptowanych dokumentów. Odświeżenie danych konta jest zastąpione
opóźnioną o 1800 ms odpowiedzią 503. Nie kontaktowano się z rzeczywistym kontem
ani bazą użytkowników. Czas wejścia kończy się po wyświetleniu treści i dwóch
klatkach przeglądarki. Nie jest pomiarem płynności animacji ani liczby FPS.

Czasy to mediany trzech kolejnych prób po próbie rozgrzewającej serwer. Główny plik
jest mniejszy o 17,7%, transfer JS przy starcie o 15,0%, a czas Startu w lokalnym
podglądzie skrócił się o 14,7%. Podgląd deweloperski wysyła wiele osobnych modułów
i przy tym spowolnieniu jest wyraźnie wolniejszy od gotowej kompilacji.

Pełne pierwsze otwarcie gotowej aplikacji nie wykazało trwałej poprawy czasu:
w pierwszej serii mediana wyniosła 1885 → 2062 ms; w dodatkowej kontroli
naprzemiennej, po cztery próby każdej wersji, 1973 → 1944 ms. Wyniki mają zbyt
duży rozrzut, aby obiecywać przyspieszenie tego etapu. Fuel, Progres i wejście
do IQ także nie wykazały jednolitej poprawy. Czasy długich zadań nie spadły
jednoznacznie. Pewne zmiany to mniejszy transfer, usunięcie powtarzanych obliczeń
i szybsze powroty między Startem a Planem w tej próbie.

Nie mierzono fizycznego iPhone'a, realnego backendu ani serwera podglądu Lovable.
Ich obciążenie i połączenie nadal wpływają na odczuwalną szybkość.

## Wgranie z telefonu

1. Rozpakuj `01-BallWise-PLYNNOSC-16.zip` w aplikacji Pliki.
2. Otwórz `jangleba/plan-pi-karza`, gałąź `main`, katalog `.github/workflows`.
3. Przez **Add file → Upload files** wgraj tylko `ballwise-plynnosc-16.yml`.
   Zapisz **Commit changes**. ZIP-a ani raportów nie wgrywaj do tego katalogu.
4. **Actions → BallWise - 16 Plynnosc aplikacji i podgladu → Run workflow → main**.
5. Poczekaj na zielony wynik. Instalator sprawdza zgodność wszystkich plików,
   nakłada zmiany, uruchamia kontrolę wydania i dopiero wtedy zapisuje je na `main`.
6. W Lovable sprawdź synchronizację z GitHub. Po jej zakończeniu otwórz podgląd
   ponownie i odśwież kartę. Sprawdź wersję `2026.10.29.16` w Profilu lub FAQ.
7. Otwórz Start, potem Plan, wróć do Startu; sprawdź także Fuel, Progres i IQ.
   Podgląd i opublikowana strona to osobne wersje: istniejąca publiczna strona
   wymaga aktualizacji przez **Publish/Update**. Dla już zainstalowanej aplikacji
   natywnej potrzebna jest nowa kompilacja iOS zawierająca te pliki.

Instalator nie korzysta z czatu AI Lovable. Obowiązują limity minut GitHub Actions
i ewentualne limity używanego hostingu. Paczka dodaje tylko ręcznie uruchamiany
workflow; nie dodaje następnej kontroli wykonywanej przy każdym pushu.

Paczka 16 jest przygotowana dla zainstalowanej paczki 15. Nie uruchamiaj ponownie
starszych instalatorów. Ponowne uruchomienie 16 rozpoznaje identyczne pliki.
Przy konflikcie z nowszą zmianą instalator kończy działanie przed zapisem
jakiegokolwiek pliku. Zachowaj komunikat z Actions do ustalenia zgodnej poprawki.

## Cofnięcie

W Actions otwórz zakończone uruchomienie i zanotuj commit instalatora. Cofnij
w GitHub commit `BallWise: plynnosc aplikacji i podgladu (paczka 16)` przez
zwykły revert lub pull request. Nie cofaj samego pliku workflow — zmiany aplikacji
są zapisane w osobnym commicie. Po synchronizacji ponownie opublikuj stronę,
jeśli była opublikowana. Paczka nie wymaga cofania migracji ani czyszczenia danych.
